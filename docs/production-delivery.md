# Production delivery

Push to `main` triggers `.github/workflows/production-delivery.yml`. After secret scanning, it calls the trusted workflow in public `tsilva/.github`, pinned to a reviewed full commit SHA. The privileged job checks out only the shared implementation, waits for the same latest main commit's CI, and syncs its fixed Production allowlist. A separate GitHub Actions job builds the exact commit, stages its prebuilt artifact on Vercel, verifies that deployment, then promotes it to production. Vercel's automatic Git deployments remain disabled so they cannot race synchronization.

Infisical remains the source of application secrets. Development uses the existing human CLI login. The shared GitHub reader has Viewer access to the assigned production vaults, and the completed rollout requires its server-side OIDC policy to match the exact approved reusable workflow revision, caller repository IDs, owner ID, main branch and Production context. The trusted `apps.json` selects the source vault and destination from the immutable caller repository ID; app files and inputs cannot change that mapping. The reader itself can access all assigned vaults inside the trusted job. The Infisical reader token stays in the trusted job, which sends the allowlisted values only to their configured Production destination. The Vercel deployment credential remains in this repository's GitHub Production environment.

The pinned shared source and [trust contract](https://github.com/tsilva/.github/blob/48a4449de4ac5f4d5e14343f70fe5fc57bc2cd74/.github/actions/production-delivery/README.md) are authoritative. App repositories retain only the pinned caller workflow. Source/destination mappings, credential handling and boundary tests are maintained centrally; no app code executes in the privileged job.

The workflow does not run on pull requests or forks, export `.env` files, upload secret artifacts, delete secret variables, or change preview/development variables. All required source keys and destination targets are checked before writes. Failed CI or sync prevents deployment. Existing production remains live on failure.

Automatic secret-change delivery uses a standalone Cloudflare Worker with a private GitHub App, independent of application deployments. Each vault's signed General webhook is restricted to `prod`, `/`, and `secrets.modified`. The relay receives event metadata and never fetches application secrets. It verifies raw-body HMACs and timestamps, stores pending routing metadata durably, coalesces bursts and retries dispatches during GitHub outages. A per-repository installation token starts only the fixed entry workflow on `main`. The relay endpoint is `https://production-deployment-relay.tsilva-production-delivery.workers.dev/infisical`. Webhook activation and per-app live verification are required before calling the automatic path operational.

Use **Actions → Production delivery → Run workflow → main** to recover after fixing a failed workflow. A relay acknowledgement confirms durable acceptance, and a GitHub dispatch acknowledgement confirms only that the run was accepted. Neither confirms deployment success. There is no polling schedule. Deployment credentials expire after one year and need rotation before expiry.

Native Infisical syncs are disabled after this workflow has successfully replaced them. Updating a deployment credential in GitHub does not replace application keys in Infisical.


Chatex first deploys Worker code in a separate app-owned job with only its existing Cloudflare credential and no OIDC permission. This job installs the locked dependencies, waits for exact-commit CI, retains existing Worker secret bindings and checks health without a paid provider call. The trusted shared job then syncs only `OPENAI_API_KEY` to `chatex-rooms` in account `83e1ce4a70ea388693e8525a772ccefa`, verifies its metadata. A separate GitHub Actions job builds the exact frontend commit and verifies the prebuilt Vercel deployment before promotion. A staging-only run checks the frontend without deploying Worker code or syncing its secret. The relay runs in a different Cloudflare account, so the Chatex deployment token cannot replace it.

## Staging a prebuilt deployment

Use **Actions → Production delivery → Run workflow → main** with **stage_prebuilt** selected to build and verify a Vercel deployment while production domains keep serving the live release. Leave the option clear for a production delivery.
